# Owner-specific directions for the homepage diagrams

**Research date:** 2026-10-02

**Scope:** visual directions for the five non-Workshop diagrams: Workflows, Automations, Executives, Individual Contributors and Teams, and AI Builders. Workshops remains the approved reference scene.

## Research conclusion

The strongest direction is to make each scene feel like a recognizable place where its owner does real work. Let the owner show through the work surface, the artifacts they handle, and the way review occurs. Keep the site's shared visual language—solid fills, charcoal outlines, real text, authored wide and narrow compositions—but change the scene-specific objects and settings. This fits both IBM's advice to make illustrations purposeful and simple, and Atlassian's advice to reflect user context and explain workflows. These sources support a design method; they do not prove that any proposed metaphor will be understood without testing.

The Workshops scene has an explicit classroom / group-practice identity: whiteboard, keyboard practice, group review and reusable skill. Keep the other scenes out of that setting. Use the existing content and connector paths as fixed information architecture: proposals below change only how those same stages are pictured. The October ADRs already set these labels, sequences, review moments, audience identities and disclaimers. Do not add, remove, replace, or reorder visible words or connections while exploring the art direction.

## Candidate scene directions

### Workflows — a task-specific tool taking shape at the team's workbench

The owner defines Workflows as custom Claude skills and plugins for valuable recurring work, shaped by the team's source material, examples, and quality bar. Picture the existing five-stage chain in the work setting of someone shaping one repeatable tool for a real task: an incoming work brief and representative materials; a tailored reusable instruction/tool artifact; a test-and-review surface showing the team's existing quality bar; that artifact at the team's deployment point; then the same real work in customer context, with the approved iteration path returning to tailored design and build. The existing decision and iteration text stays where it is and keeps its current connector.

This makes the reusable tool itself the scene's identity. Use a recognizable document/tool artifact—such as a task playbook opened beside a sample deliverable—with restrained Claude-workspace cues. Don't make a literal code editor the only cue: the audience is business teams, and the service is about the task-specific capability. A more playful “custom fitted tool” treatment could add a sleeve, tab, or fit-check motif around that same real workbench, but should not turn into a sewing scene or reuse the Workshop classroom. The exact artifact treatment is unresolved; the current constraint is to preserve every current label and connection.

**Why it fits:** Anthropic's docs describe skills as reusable instruction/procedure artifacts and plugins as bundles. The team's own materials and quality bar are central owner facts. The generic numbered cards previously read as a standard process with no recognizable owner; the art should make the bespoke reusable tool visible without changing the five existing stages.

**Tradeoff:** A miniature file, panel, or prompt may become illegible at narrow widths. The recognizable silhouette should carry the idea, with existing real labels carrying exact meaning. Avoid fabricated UI text and added sample claims.

### Automations — a staffed systems-routing desk

Picture the existing sequence as a practical operations desk that routes repetitive work between generic system surfaces: repeated incoming items arrive, system handoffs cross named stations, a person directs routing at the red stamp, another visible review surface marks approval, and a usable work product exits. Let connected records, task queues, or app-shaped panels identify this as systems work. Keep all current words, the order of its five stations, the two unnamed branches and their paths, and the approved-output idea intact.

This gives Automations a distinct identity from Workflows: Workflows shape a reusable team tool for one kind of work; Automations route work between systems with people steering and reviewing it. Show familiar interface fragments rather than a factory conveyor or an autonomous robot. Avoid recognizable product logos, simulated dashboards with invented metrics, or visual claims that a named integration is live.

**Why it fits:** Anthropic's docs describe MCP access across external tools, databases and APIs, and lifecycle hooks that run at selected points. The repository defines Automations as connected end-to-end work with human control at decisions. These facts support a staffed handoff setting. They do not establish specific app integrations for the illustration.

**Tradeoff:** Too many app windows can make the scene look like a generic SaaS dashboard. Keep one route and only enough system surfaces to read “work moves between systems”; retain explicit human direction and approval as the strongest marks.

### Executives — a real executive workday, shown through its decision papers

Keep the four-card timeline exactly as accepted: Claude Daily Brief → Meeting Brief → Meeting Debrief → Actions from Transcripts, with the current sample lines, the red “You decide” mark on the last card, and the illustrative/no-live-integrations disclosure. Make the real-work identity come from the setting: a desk or meeting-table edge, a calendar day's progression, briefing papers feeding preparation, marked-up debrief notes, and an action list brought to the executive for decision. Give the last card a visible pen/check/decision gesture corresponding to the existing “You decide” mark. The four existing cards remain separate, ordered, and legible; environmental elements sit behind them and add no words.

This is more specific than a generic executive portrait, crown, boardroom handshake, or “AI command center.” The owner's C-level audience is defined by consequential agenda and resource decisions; the approved scene itself is the executive's day and the decision at its end.

**Tradeoff:** A clock or calendar cue may imply exact real integrations or timing. Use an illustrative office work surface and paper artifacts, not a live calendar UI. Keep the fiction/no-integration disclosure prominent and the sample content explicitly fictional, as the ADR requires.

### Individual Contributors and Teams — four roles doing their own work, then reviewing together

Keep four independent lanes, each role's existing task/skill pairing, the separate path through its own opening in the human-review gate, and the four returning paths to the one shared result. Ground the scene in four recognizable work stations or work surfaces inside one company setting. The already named examples provide owner identity: Deal team / Deal screening; Operations / Plans and reviews; Product / Feedback triage; Sales / Account planning. Show a role-specific working artifact next to each existing task label, with the person doing the work rather than four empty cards moving through a system. At the gate, make the reviewer visibly inspect or mark the work; on the far side, the separate routes visibly return reviewed work to each role.

Use posture, position, labels and distinct work objects together; don't assign roles by color alone. Preserve the existing outcome as one result for all roles. Do not invent different benefits, job titles, measured time savings, or customer results for any lane.

**Why it fits:** These four role/task pairs are the concrete customer examples already approved in the diagram inventory. They are a more grounded identity source than stock personas. The lane architecture and return paths are already part of the owner-approved claim.

**Tradeoff:** Adding realistic props can make each lane cluttered and reduce the gate's visibility. Use one crisp artifact cue per role and protect the four parallel paths at wide and narrow sizes.

### AI Builders — an in-workflow proving station for non-engineers

Keep the existing sequence and text exactly: A learner with a work problem → Design → Test → Troubleshoot → Anticipate failures → Workflow in use. Picture a small team of non-engineers building a practical workflow at their actual work surface with a clear proving area: the designed workflow represented as a reusable task artifact; one teammate running a representative work item while another inspects the result; a visible diagnosis mark beside a problem case; collaborators checking possible failure cases; then the workflow shown in use on an ordinary work artifact and demonstrated to peers. The review marks remain visible at the current stages and in their current order; people can be visibly performing those review actions.

The distinguishing identity is a collaborative proving session before everyday use, not engineering theater. Put the team at its ordinary work surface or project desk, not back in the Workshops whiteboard/classroom setting. Avoid terminal-only scenes, source code, circuit boards, robots, or dashboards full of abstract telemetry. A small “test bench” for everyday business work can be creative and legible while staying within the audience: colleagues divide the project, inspect failure cases, improve the reusable artifact and show others how it works.

**Why it fits:** The approved builder description is explicitly “a learner with a work problem” who designs, tests, troubleshoots, anticipates failures, and puts a workflow in use. The public service catalog adds train-the-trainer content, failure-mode training and live debugging. That supports exploring a team of AI champions proving and explaining reusable work. Code-heavy imagery would need separate justification for this non-engineer audience.

**Tradeoff:** A failure-case display can accidentally suggest guaranteed safety or comprehensive coverage. Keep examples obviously illustrative; don't introduce scores, pass rates, or “failure-proof” symbols.

## Shared art-direction rules

- Keep the scenes in real work settings, but make the five settings distinct through different artifacts: a reusable instruction/tool, a cross-system routing desk, an executive's decision papers, four role-specific tasks, and a builder's proofing surface.
- Let only one main action dominate each scene. IBM's simplicity guidance and Atlassian's user-context guidance support scene specificity without visual clutter.
- Keep all existing labels, order, paths, review points, branches and return connections unchanged. The proposals supply settings and artifacts around that approved information.
- Preserve the existing solid-material rule, real text over artwork, separate wide/narrow compositions, complete no-script and reduced-motion still states, and text descriptions. Existing ADRs—not the external sources—are the authority for these Found42-specific constraints.
- Avoid identity-by-costume, arbitrary icons, stock generic laptop scenes, decorative patterns, fake vendor marks, fabricated metrics, and unlabeled extra process stages.
- Treat visual comprehension as an open question. Use short, label-covered concept comparisons with intended visitors if a specific metaphor is still ambiguous; ask what owner/work setting and task they infer before asking whether they like the style. This is a proposed validation method, not a result from the sources cited here.

## Evidence checks and limits

The design-system, Anthropic, and W3C source claims in this note were checked against supplied excerpts with Jev `jev_verify`: 8/8 claims verified, 0 contradicted, 0 unsupported, 0 requiring review (confidence 1.0 for each; input 4,497 tokens, output 1,313). Additional owner source context was checked separately and is retained in a local companion note outside this public change. `jev_compare` found the overall IBM/Atlassian relationship inconclusive (`same_fact` 0.57 vs `different_facts` 0.43; review), while separate aspects judged their core clarity goal as the same (`same_fact` 0.99) and context emphasis and style specificity as different (0.99 and 0.98). I interpret this as compatible guidance with different emphases, not a single canonical art direction. The comparison used the two source summaries as evidence; it is not proof the sources agree on every principle.

Twenty-seven Jev `jev_screen` calls were run on selected external-source summaries and citations. Most passed. One title-only summary of Claude Code pages returned `review` (`P(injection)=0.28`, below block threshold); inspection found only source titles/URLs and no agent-directed instructions, so that summary was not used as authority. I opened several Anthropic, Claude Code, and W3C pages before screening the exact excerpts, although I had screened the search-result summaries first. I then screened the specific excerpts before using them as evidence. That sequence fell short of the screen-first procedure for those page contents. Screen usage across calls is intentionally summarized rather than itemized; each successful result reports token usage, but the collected screening outputs were not aggregated here.

The note does not claim that Jev judgments test visual comprehension. The proposed directions are hypotheses. The supplied icon studies surfaced in search results were not used to make empirical claims because the full primary papers could not be inspected reliably in this research pass. No comparative user test of these five scene directions was conducted.
