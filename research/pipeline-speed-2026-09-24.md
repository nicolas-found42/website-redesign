# Faster verification and deployment: research, 2026-09-24

## Current path and measured baseline

The repository uses Vite, TypeScript, Playwright, and GitHub Pages. The single [`verify` job](../.github/workflows/pages.yml) installs npm packages and Chromium, Firefox, and WebKit; typechecks; runs the full suite; builds again; and uploads `dist` on `main`. The dependent `deploy` job publishes the Pages artifact. [`playwright.config.ts`](../playwright.config.ts) starts a Vite development server and a strict static server; the latter command runs `npm run build` before the tests. The build script itself runs `tsc --noEmit`, `vite build`, and prerendering. Thus a successful workflow typechecks three times and builds production output twice, although the extra work is small compared with browser testing. These are observations of this repository, not vendor benchmarks.

[`npx playwright test --list`](https://playwright.dev/docs/test-cli) currently lists **308 tests**: 100 in each of Chromium, Firefox, and WebKit, plus 8 in the unit project. The current Playwright run reports **2 workers**. In the [latest successful PR run](https://github.com/nicolas-found42/website-redesign/actions/runs/36011847223/job/107674275192), `npm test` took **493 seconds** (14:19:52–14:28:05), browser installation **57 seconds**, `npm ci` **5 seconds**, standalone typecheck **2 seconds**, and the final build **4 seconds**. The [latest `main` run](https://github.com/nicolas-found42/website-redesign/actions/runs/36012101736) spent about **492 seconds** in tests, **42 seconds** installing browsers, and **61 seconds** in Pages deployment. The 61-second deployment is a recent outlier; earlier observed deployments were about 6–7 seconds. These timestamps are rounded to the nearest second and include step startup/teardown.

The dominant opportunity is therefore the eight-minute Playwright suite. Optimizing `npm ci`, npm caching, TypeScript, or the second build alone cannot greatly change the end-to-end time. The recent `main` run took roughly 10½ minutes from creation to successful deployment, including job transition and the deployment outlier. [Run evidence](https://github.com/nicolas-found42/website-redesign/actions/runs/36012101736).

The workflow runs the same full suite on a PR and again after that PR merges to `main`; this second run adds about eight minutes to the publish path. As of September 24, the repository's [branch-protection API endpoint](https://api.github.com/repos/nicolas-found42/website-redesign/branches/main/protection) returns 404 and the [repository rulesets API](https://api.github.com/repos/nicolas-found42/website-redesign/rulesets?includes_parents=true) shows only a disabled `default` ruleset. Therefore the repo's written PR policy is not yet enforced as a required GitHub check. This snapshot must be rechecked before changing the deployment gate.

## Deployment and workflow details

- **Keep the publish dependency.** GitHub Pages' documented custom workflow builds and uploads the static artifact, then runs `deploy-pages` from the default branch; jobs depending on successful checks run after them. The Pages upload can be prepared in parallel with sharded tests, but the deploy job must wait for the full gate. [GitHub Pages publishing](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site); [Actions job dependencies](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs#defining-prerequisite-jobs).
- **Preserve failure evidence per shard.** The current job uploads `test-results/` and the HTML report when tests fail. With shards, use uniquely named artifacts; Playwright's blob reporter can merge per-shard results into an HTML report. Arrange report collection to run even when a shard fails, while making deployment depend on successful test jobs. [Playwright sharding and merge example](https://playwright.dev/docs/test-sharding#github-actions-example).
- **Avoid a blind worker increase.** Playwright explicitly recommends conservative CI worker counts for stability and proposes sharding across jobs for wider parallelism. This suite has recently caught WebKit timing and layout races, so test a higher per-runner worker count only after measuring failure rate and CPU pressure. [Playwright CI workers](https://playwright.dev/docs/ci#workers); [parallelism](https://playwright.dev/docs/test-parallel#limit-workers).
- **Do not apply a path filter to a required workflow without redesigning the required check.** GitHub documents that a workflow skipped by path filtering leaves its check pending and can block a protected PR. A fast job that always reports and conditionally skips expensive internals requires careful check naming and branch-rule review. [GitHub Actions workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore).
- **Treat Pages deployment latency separately.** The latest 61-second deploy step is an outlier against earlier 6–7-second steps. Measure more runs before engineering around it; tests and browser provisioning dominate the repeatable portion. [Latest run](https://github.com/nicolas-found42/website-redesign/actions/runs/36012101736).

## Suggested first experiment and decision rule

1. Add a diagnostic duration report and establish the slowest files/browser projects on CI. Preserve the current 308-test coverage and failure evidence.
2. Trial four Playwright shards on a feature branch, keeping current servers and browsers. Use unique failure artifacts and one required aggregate gate. Measure the **slowest shard plus setup and report handoff** over at least three runs, including a `main` deployment run if the workflow layout changes.
3. If the slowest shard is much longer than the others, split a heavy independent file or enable `fullyParallel` only for a proven safe project/suite, then remeasure. Playwright warns file-level sharding can be unbalanced; test-level sharding can balance it but runs tests in separate workers and repeats hooks. [Sharding](https://playwright.dev/docs/test-sharding#balancing-shards); [parallel tests within a file](https://playwright.dev/docs/test-parallel#parallelize-tests-in-a-single-file).
4. Remove the duplicate build and compare a pinned container to the current installation only after the sharded gate is stable. Keep whichever reduces **end-to-end** time without increasing failures.
5. Separately, enforce the PR check in GitHub branch rules and decide whether the full suite can be omitted from `main` in favor of a fresh build plus strict production smoke check. Do this after verifying that every merge path is covered and the tested SHA cannot become stale.

**Success criterion:** substantially lower median PR verification wall time (for example, under five minutes) with the same 308 test cases, same three browser engines, strict production-route checks, and no increase in reruns or flaky failures. The numeric target is a proposed experiment threshold, not a documented vendor guarantee.
