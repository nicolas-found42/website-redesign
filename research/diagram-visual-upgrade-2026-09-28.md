# Homepage diagram visual upgrade: research findings

- **Prepared:** 2026-09-28
- **Scope:** seven homepage diagrams (hero, three audience cards, three service panels).

**Evidence labels:** **Verified** means documented in a primary source or project file; **Observed** means directly inspected in a live site during this research; **Inference** means a recommendation based on those findings.

## Recommendation

**Inference:** Keep every label as DOM text and use inline SVG for the custom pictograms, with approved static arrows and tactile paper cards. Use short CSS `transform` and `opacity` transitions or keyframes for card/object movement; use TypeScript only to toggle movement state or observe visibility when needed, and do not call Motion's JavaScript API. Keep each diagram complete and legible without JavaScript, and keep reduced-motion and the site's pause control tied to a stable state ([`src/motion-preference.ts`](../src/motion-preference.ts)). Do not animate a line along the route, add a glow, or use traveling particles. Those treatments conflict with the requested editorial, human-directed feel.

The seven label sequences and their order are content, not decoration: preserve the approved text in [`src/homepage/approved.ts`](../src/homepage/approved.ts). Keep decorative SVGs hidden from assistive technology where their meaning is already expressed by the labels. The accepted mockup defines the diagrams as simple static diagrams; its presentation decision supersedes earlier homepage art-direction proposals ([ADR 0006](../docs/adr/0006-approved-homepage-mockup.md), [prior art-direction research](art-direction-2026-09-14.md), [prior motion-library research](motion-libraries-2026-09-14.md)). The current visual system is editorial and restrained; avoid reintroducing the grid and grain treatments previously removed ([`docs/DESIGN.md`](../docs/DESIGN.md), [ADR 0005](../docs/adr/0005-approachable-visual-voice.md)).

## What the research supports

### Verified project and platform facts

- The project is a Vite and TypeScript site with [`motion`](../package.json) already installed. GitHub Actions builds and deploys the static output from `dist` ([`pages.yml`](../.github/workflows/pages.yml)). **Inference:** no separate rendering engine is needed for seven small diagrams.
- GitHub Pages publishes static files and supports a custom build through GitHub Actions; it does not run server-side application code. Its current published-site limit is 1 GB, the deployment timeout is 10 minutes, and its soft bandwidth limit is 100 GB per month. The 10-builds-per-hour soft limit does not apply to a custom Actions build. ([GitHub Pages site creation and MIME documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site), [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [custom Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages))
- The Actions Pages artifact has a separate upload constraint: its tar file must be under 10 GB. The Pages-published site still must be no larger than 1 GB. The custom workflow also requires `pages: write` and `id-token: write` for deployment, with the deploy job dependent on the build job; the current workflow follows that pattern. ([GitHub custom Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [project workflow](../.github/workflows/pages.yml))
- GitHub Pages chooses MIME types from `mime-db`; the site owner cannot set a custom MIME type for an individual file or repository. If a future implementation adds `.wasm`, inspect the deployed response's `Content-Type`; WebAssembly streaming requires `application/wasm`. ([GitHub Pages MIME documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site), [WebAssembly Web API](https://webassembly.github.io/spec/web-api/), [Emscripten deployment guidance](https://emscripten.org/docs/compiling/Deploying-Pages.html))
- SharedArrayBuffer and related cross-origin-isolated APIs require `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` or `credentialless`. A GitHub staff response says custom response headers are not supported on Pages; this is a staff answer in a community discussion, rather than a guarantee stated in the Pages documentation. Avoid relying on threaded Wasm on this host unless the hosting configuration changes; a single-thread implementation would avoid that header requirement. ([MDN `crossOriginIsolated`](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated), [GitHub staff response on custom headers](https://github.com/orgs/community/discussions/54257))
- The current production build uses the `/website-redesign/` base path ([`vite.config.ts`](../vite.config.ts), [`src/paths.ts`](../src/paths.ts)). **Implementation implication:** any future external modules, workers, or runtime assets would need to resolve under that project subpath.
- Motion's JavaScript `animate()` supports HTML and SVG, and its hybrid API supports transform and SVG path animation. The documentation lists a 2.3 KB mini build and an 18 KB hybrid build. **Inference:** since Motion is already installed, adding another library would duplicate animation capability. ([Motion `animate()` documentation](https://motion.dev/docs/animate))
- For brief movement, web.dev recommends prioritizing `transform` and `opacity`, which avoid the layout/paint work caused by many other animated properties. `prefers-reduced-motion` is the platform signal for users who request less nonessential motion. ([web.dev animation guide](https://web.dev/articles/animations-guide), [MDN `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion))
- Canvas needs useful fallback or sub-DOM content for users who cannot experience its drawing as intended. WebGPU is not Baseline and requires a secure context, so using it would need feature detection and a fallback. ([MDN Canvas accessibility guidance](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Basic_usage), [MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API))
- Rust/Wasm and C++/Emscripten are real browser targets, but they still cross into browser APIs: `wasm-bindgen` exposes DOM APIs through bindings, while Emscripten emits JavaScript runtime glue alongside Wasm output. **Inference:** those toolchains solve compute or portability needs, not the presentational needs of these flows. ([wasm-bindgen DOM example](https://rustwasm.github.io/docs/wasm-bindgen/examples/dom.html), [Emscripten deployment guidance](https://emscripten.org/docs/compiling/Deploying-Pages.html))

### Live visual and interaction observations — 2026-09-28

- **Course Diagram Animated (Dribbble):** The inspected preview uses large alternating yellow and charcoal icon medallions with compact step labels and subordinate text. The scale contrast makes each node readable as an editorial object. **Inference:** borrow the icon emphasis and restrained alternating fills, not a luminous or traveling route treatment. ([live reference](https://dribbble.com/shots/26769321-Course-Diagram-Animated))
- **Stripe Connect product page:** I directly inspected the production [Connect landing page](https://stripe.com/connect) at 1440 × 1000. Its light, spacious first viewport pairs a large heading with a detailed product card and customer, merchant, and payment labels connected by thin, static strokes. **Inference:** this is a useful reference for keeping a relationship diagram subordinate to the page heading while making its labels easy to scan; retain Found42's paper-card palette and restrained pictograms.
- **Stripe's Connect animation case study:** Stripe's first-party [engineering post](https://stripe.com/blog/connect-front-end-experience) documents the production page's rotating CSS 3D cubes with per-frame face visibility, transform, and shading, plus a code-built onboarding walkthrough using the Web Animations API and Intersection Observer. This is a complex authored-motion example and a useful source on choosing techniques: the post recommends CSS transitions for simple movement and reserves richer JavaScript-driven animation for cases that need interactivity or custom effects. **Inference:** these homepage diagrams do not need that complexity; a small CSS transform/opacity reveal is sufficient.
- **Unistep BPMN customer-relations demo:** The live example exposes step count plus Previous, Step, Run, Pause, Rewind, and Stop controls over a multi-lane process diagram. **Inference:** explicit step state and user control are useful interaction patterns when a process needs explanation; the dense BPMN visual language is not a fit for Found42's small marketing diagrams. ([live demo](https://www.unistep.eu/en/demos-en/BPMN3-Customer-relation/BPMN3-Customer-relation.html))
- **Simulaction quick-start editor:** The inspected demo presents a numbered walkthrough, a play control, a focused diagram item, and a caption. **Inference:** tying one brief motion to a corresponding readable label can explain a stage without animating a route continuously. The editor's app chrome is not a visual reference for the homepage. ([live demo](https://app.simulaction.io/editor?demo=quick-start), [product site](https://simulaction.io/))

### Implementation comparison

| Approach                                 | Capability and fit                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Trade-off for these seven diagrams                                                                                                                                                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **HTML + CSS + inline SVG**              | Text stays in the document; SVG provides crisp custom pictograms; CSS can move the card/object with `transform` and `opacity`. ([MDN Canvas fallback guidance](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Basic_usage), [web.dev animation guide](https://web.dev/articles/animations-guide))                                                                                                                                            | **Recommended.** Keep all approved labels present before enhancement, use short CSS motion only, and make no Motion API call.                                                                                                                          |
| **Motion / Web Animations API**          | Motion can animate HTML/SVG; its hybrid API supports path animation. Stripe's production write-up used the native Web Animations API for a richer interactive walkthrough. ([Motion docs](https://motion.dev/docs/animate), [Stripe engineering post](https://stripe.com/blog/connect-front-end-experience))                                                                                                                                                       | Existing Motion is available, but is unnecessary for brief card/object movement. Avoid animated route paths even though the APIs support them.                                                                                                         |
| **Canvas / WebGL / WebGPU**              | WebGL targets interactive 2D/3D graphics through canvas and can use device graphics acceleration; WebGPU support is incomplete and secure-context-only. Canvas needs fallback/sub-DOM for accessible meaning. ([MDN WebGL](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API), [MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API), [MDN Canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Basic_usage)) | **Inference:** a separate renderer and text/accessibility layer have no demonstrated need for these diagrams. Do not use for these flows.                                                                                                              |
| **Authored runtime (Rive or dotLottie)** | Rive state machines can be controlled through inputs in JavaScript; its web examples render to canvas. dotLottie uses a Wasm engine of about 500 KB compressed, fetched from a CDN when a player is constructed. ([Rive state-machine guide](https://github.com/rive-app/help-center/blob/master/runtimes/state-machines.md), [dotLottie web README](https://github.com/LottieFiles/dotlottie-web/blob/main/packages/web/README.md))                               | Makes sense for bespoke character animation or motion authored by a dedicated designer. For static icons and short card movement, it adds an authoring format, runtime, asset loading, and canvas-to-DOM coordination without improving label clarity. |
| **Rust or C++ compiled to Wasm**         | Both toolchains can produce browser-run Wasm; DOM integration still happens through JavaScript/browser bindings, and WebAssembly streaming relies on the proper MIME type. ([wasm-bindgen DOM example](https://rustwasm.github.io/docs/wasm-bindgen/examples/dom.html), [Emscripten Pages deployment](https://emscripten.org/docs/compiling/Deploying-Pages.html), [WebAssembly Web API](https://webassembly.github.io/spec/web-api/))                             | Good for compute-heavy or portable algorithms. No such workload exists here; adds build, MIME, and possibly header/isolation concerns without improving the editorial art.                                                                             |

## Discovery sources

GitHub awesome lists were used only to discover candidate approaches; their inclusion is not evidence of quality or compatibility. The consulted collections covered creative coding, web design and visual style, CSS animation, SVG animation, general web animation, Canvas, WebGL, WebGPU, and Rust/Wasm: [awesome-creative-coding](https://github.com/terkelg/awesome-creative-coding), [awesome-web-design](https://github.com/brandonhimpfen/awesome-web-design), [awesome-design](https://github.com/gztchan/awesome-design), [awesome-css-animations](https://github.com/streamich/awesome-css-animations), [awesome-svg animation topic](https://github.com/willianjusten/awesome-svg/blob/master/topics/Animation.md), [awesome-web-animation](https://github.com/sergey-pimenov/awesome-web-animation), [awesome-canvas](https://github.com/raphamorim/awesome-canvas), [awesome-webgl](https://github.com/sjfricke/awesome-webgl), [awesome-webgpu](https://github.com/mikbry/awesome-webgpu), and [awesome-rust-and-webassembly](https://github.com/rustwasm/awesome-rust-and-webassembly).

The visual and technical conclusion is to keep these diagrams as HTML/SVG illustrations that feel like crafted paper objects, with arrows that remain still and CSS movement that briefly settles the objects into place. That preserves the existing content and host, supports narrow layouts, and avoids introducing a GPU or Wasm runtime solely for decoration.
